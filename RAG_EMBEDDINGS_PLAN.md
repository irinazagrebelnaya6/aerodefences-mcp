# План: перехід RAG з TF-IDF на повноцінні embeddings

**Гілка:** `feat/rag-embeddings`
**Статус:** реалізовано — фази A → E (усі, включно з semantic cache).

---

## 1. Поточний стан і мотивація

Зараз `rag_index.py` — in-memory **TF-IDF + косинус** (чистий Python, без
залежностей). Це прозоро й детерміновано, але:

- **Немає семантики.** «дрон для розвідки вночі» не знайде «БПЛА з
  тепловізором», якщо не збігаються токени — рятують лише ручні синоніми
  (`knowledge/synonyms.md`), які треба постійно поповнювати.
- **Крос-мовний розрив.** Описи товарів англійською, запити українською —
  TF-IDF це не долає (знов-таки латаємо синонімами).
- **Морфологія.** Без стемінгу «акумулятора» ≠ «акумулятор».

Embeddings знімають усі три проблеми: багатомовна модель кладе укр-запит і
англ-опис у спільний векторний простір, синоніми стають непотрібними як
милиця (файл лишається, але перестає бути критичним).

## 2. Ключові рішення

| Рішення | Вибір | Чому |
|---|---|---|
| **Бекенд** | Зовнішній API — **Voyage AI** (`api.voyageai.com/v1/embeddings`) | Рекомендований провайдер в екосистемі Anthropic (Anthropic власного embeddings API не має); найкраща якість без важких локальних залежностей |
| **Модель** | **`voyage-4-lite`** (дефолт), `voyage-4` — опція через env | Багатомовна (укр ✓), 32k контекст, 1024-вимірні нормовані вектори; $0.02/1M токенів, перші **200M токенів безкоштовно** — наш корпус (~50–100k токенів) коштує $0 |
| **HTTP-клієнт** | Уже наявний **`httpx`** (транзитивна залежність fastmcp), без пакета `voyageai` | Філософія проєкту — мінімум залежностей; API — один POST-ендпоінт |
| **Лінійна алгебра** | Чистий Python (dot product) | ~80 документів × 1024 float — numpy не потрібен; вектори Voyage нормовані, тож косинус = скалярний добуток |
| **Fallback** | TF-IDF лишається як бекенд за замовчуванням | Офлайн-режим, CI без секретів, деградація при недоступності API |

### Нові змінні оточення

| Змінна | Призначення | Дефолт |
|---|---|---|
| `ADD_RAG_BACKEND` | `tfidf` \| `voyage` | `tfidf` (нічого не ламається без ключа) |
| `VOYAGE_API_KEY` | Ключ Voyage AI | — (без нього `voyage`-бекенд не стартує — fail-safe, як із JWT) |
| `ADD_EMBED_MODEL` | Модель ембедінгів | `voyage-4-lite` |
| `ADD_EMBED_DIM` | Розмірність (256/512/1024/2048) | `1024` |

Порожній рядок = «не задано» (використовуємо вже наявний `opt()` з `ad_config`).

## 3. Фази

### Фаза A — абстракція Retriever (без зміни поведінки)

1. У `rag_index.py` виділити інтерфейс бекенда:
   `build(corpus) / search(question, k) / status()`.
2. Наявний TF-IDF-код → клас `TfidfBackend` (логіка 1:1, збір корпусу
   з БД+файлів спільний і виноситься з бекенда — він однаковий для обох).
3. `RagIndex` стає тонким фасадом: обирає бекенд за `ADD_RAG_BACKEND`.
4. **Критерій готовності:** усі 11 тестів зелені без жодної зміни, дефолтна
   поведінка байт-у-байт та сама.

### Фаза B — VoyageBackend

1. `_embed(texts, input_type)` через `httpx.AsyncClient` →
   `POST /v1/embeddings` (`Authorization: Bearer $VOYAGE_API_KEY`).
   - Корпус ембедимо з `input_type="document"`, запит — `input_type="query"`
     (Voyage додає різні префікси — це важливо для якості retrieval).
   - Батчами (ліміт API — до 1000 текстів/запит; нам вистачить одного батча).
   - Таймаут 30с, 2 ретраї з backoff на 429/5xx.
2. `search()`: ембед запиту → dot product по векторах корпусу → top-k
   (той самий формат результату: `doc_id`, `source`, `title`, `score`,
   `snippet` — **контракт інструмента `ask_catalog` не змінюється**).
3. Обробка збоїв: якщо API недоступний під час build — лог `log.warning`
   і **автоматичний fallback на TfidfBackend** (сервер живий завжди);
   якщо збій на запиті при готовому індексі — помилка запиту, індекс не
   руйнуємо.
4. Безпека: ключ ніколи не логуються; назовні — нейтральне
   `embeddings backend unavailable` (як зробили з `database unavailable`).

### Фаза C — кеш ембедінгів (не платити і не чекати повторно)

1. Дисковий кеш `.cache/rag_embeddings.json` (у `.gitignore`):
   ключ — `sha256(model + dim + text)` кожного документа.
2. `rebuild_rag_index` пере-ембедить **лише змінені** документи
   (після `update_price`/`update_stock` тексти товарів змінюються точково).
3. Запити (`ask_catalog`) точним збігом не кешуємо — вони дешеві (~20 токенів)
   і текстуально завжди різні; семантичне кешування запитів — окрема Фаза E (§4).
4. Multi-replica заувага в PRODUCTION.md §5.3 лишається чинною: кеш —
   per-replica; для реплік — спільний том або Redis (уже передбачений).

### Фаза D — оцінка якості, тести, документація

1. **Golden set**: ~15 українських запитів із очікуваним `doc_id`
   (`tests/golden_queries.json`), включно з «важкими» крос-мовними
   («тепловізійна камера» → продукт з англ. описом thermal imaging).
2. Скрипт `docs/verification/eval_rag.py`: hit@1 / hit@5 для `tfidf` vs
   `voyage` на golden set — числовий доказ поліпшення для звіту.
3. Тести: юніт-тести бекенда з **мокнутим** httpx (без мережі, CI зелений
   без ключа); опційний інтеграційний тест під
   `@pytest.mark.skipif(not VOYAGE_API_KEY)`.
4. Docker/CI: у `docker-compose.yml` прокинути `ADD_RAG_BACKEND`,
   `VOYAGE_API_KEY` через env (секрет не в образі); CI лишається на `tfidf`.
5. Оновити README, ARCHITECTURE §RAG, PRODUCTION (нові env, кеш, fallback).

## 4. Мікросервісні патерни для LLM: де застосовні в цьому проєкті

Чотири класичні патерни інтеграції LLM у мікросервісну архітектуру та їхнє
місце в AeroDefences MCP:

| Патерн | Яку проблему розв'язує | Застосування тут |
|---|---|---|
| **API Gateway** | Маршрутизація запитів до різних моделей (GPT, Claude, Llama): єдина точка входу, автентифікація, ліміти, вибір моделі за задачею/вартістю | Обмежено: у нас одна модель-хост (Claude) і один embeddings-провайдер. Стане актуальним, якщо додамо другий embeddings-бекенд — gateway обиратиме Voyage vs локальну модель |
| **Sidecar** | Винесення наскрізної логіки (токенізація, кешування) в окремий контейнер поруч з основним — сервіс лишається чистим | ✅ **Реалізовано:** контейнер `embeddings` (`sidecar/`, свій Dockerfile) тримає клієнт Voyage + кеш; mcp ходить по HTTP (`ADD_EMBEDDINGS_URL`). Профіль `voyage` у compose; ключ Voyage — лише в sidecar |
| **Event-Driven (Kafka/RabbitMQ)** | Довгі генерації / async processing: не тримати HTTP-з'єднання, не втрачати роботу при обриві, розв'язати продюсера й воркерів | ✅ **`rebuild_rag_index`**: подія `catalog.updated` у чергу → усі репліки перебудовують індекс консистентно. Це прямо закриває проблему PRODUCTION.md §5.3 (індекс per-replica). Поки що реплік мало — достатньо Redis pub/sub, без Kafka |
| **Semantic Cache (Redis)** | Повторні дорогі виклики LLM для *семантично однакових, але текстуально різних* запитів («скільки коштує X» ≈ «яка ціна X») — точний кеш їх не ловить | ✅ **`ask_catalog`** — див. Фазу E нижче. Інфраструктура вже є: `ADD_REDIS_URL` передбачений для multi-replica сесій |

### Фаза E (опційна) — Semantic Cache для `ask_catalog`

Механіка:
1. Запит ембедиться (це вже відбувається у Фазі B — додаткових викликів немає).
2. У Redis шукаємо серед збережених векторів запитів найближчий
   (косинус ≥ **0.93** — поріг тюнимо на golden set з Фази D).
3. Влучання → повертаємо збережений результат retrieval без пошуку по індексу;
   промах → звичайний пошук, після чого пишемо в кеш
   `(вектор запиту, результати, TTL)`.

Що це дає:
- **Вартість**: нуль повторних викликів embeddings API на перефразовані запити.
- **Latency**: мілісекунди замість round-trip до API.
- **Спільність між репліками**: Redis один на стек — кеш працює для всіх,
  на відміну від in-memory індексу.

Інвалідація (критично, бо каталог змінюється):
- **TTL** за замовчуванням 1 година (`ADD_SEMCACHE_TTL`).
- **Скидання на write**: кожна write-операція (`update_price`, `update_stock`,
  `bulk_set_status`…) уже проходить через єдиний бар'єр у `ad_tools_write` —
  туди додається `FLUSHDB`-подібне очищення простору ключів кешу
  (`semcache:*`). Грубо, але корпус малий і безпечність відповіді важливіша
  за hit rate.
- Поріг схожості свідомо високий: false positive (відповідь на *інше*
  питання) гірший за cache miss.

Нові env: `ADD_SEMCACHE=on|off` (дефолт `off`), `ADD_SEMCACHE_TTL` (сек),
поріг `ADD_SEMCACHE_THRESHOLD` (дефолт `0.93`). Працює лише коли задані
`ADD_REDIS_URL` **і** бекенд `voyage` (для TF-IDF семантичний кеш не має
сенсу — вектори не переносяться між перебудовами індексу).

Коміт: `feat(rag): semantic cache for ask_catalog via Redis (phase E)`.

**Статус: реалізовано.** `ad_semcache.py` (Redis-backed `SemanticCache`),
інтеграція в `ask_catalog` (вектор запиту переиспользується — без подвійного
ембедингу), Event-Driven інвалідація в єдиному write-барʼєрі
`Database.run_write` (`invalidate_semcache`). Тести — `tests/test_semcache.py`
з in-memory фейком Redis (без мережі).

## 5. Що свідомо НЕ робимо (зараз)

- **Векторна БД** — ✅ **додано опційно (`ADD_RAG_BACKEND=qdrant`, `ad_qdrant.py`):**
  Qdrant як окремий контейнер, ANN-пошук по REST. На ~80 документів це overkill
  (дефолт лишається `tfidf`), але демонструє повноцінну мікросервісну архітектуру
  з винесеним у vector-DB retrieval.
- **Reranker** (`rerank-2.5`) — має сенс лише при великому корпусі.
- **Локальна ONNX-модель** — відхилено на користь API (рішення зафіксовано).
- **Видалення TF-IDF** — лишається як офлайн-fallback і база для порівняння.

## 6. Ризики

| Ризик | Пом'якшення |
|---|---|
| API недоступний / нема ключа | Дефолт `tfidf`; авто-fallback при збої build |
| Витік ключа | Ключ лише через env, не в образі/логах/репо |
| Дрейф вартості | Корпус мікроскопічний; free tier 200M токенів; лічильник токенів з відповіді API — у `metrics` |
| Недетермінованість у CI | CI не торкається мережі: моки + `tfidf` |
| Зміна якості видачі | Golden set + eval-скрипт до/після (Фаза D) |

2. `feat(rag): Voyage AI embeddings backend with tfidf fallback (phase B)`
3. `feat(rag): disk cache for document embeddings (phase C)`
4. `test(rag): golden-set eval tfidf vs embeddings + docs (phase D)`
